# Research file and application integrations

Type: research
Status: resolved
Blocked by: none

## Question

What stable Raycast or macOS mechanisms should implement Quick Look, copy path, move to Trash, default-open, choose-application, and opening a selected directory in terminal or IDE applications such as Ghostty, Zed, and T3 Code? Produce an integration matrix covering availability detection, arguments or URLs, cancellation, permission errors, and recoverable failure behavior.

## Comments

## Answer

### Decision

Use Raycast's built-in file actions and system utilities as the primary integration layer. They already delegate application choice and opening to macOS Launch Services, so the extension does not need Finder, shell quoting, or Apple Events for normal file access. Resolve applications by bundle ID, not display name or install path. Store only the bundle ID in preferences and resolve the current `Application` object again with `getApplications()`.

| Capability | Primary invocation | Availability and cancellation | Permissions and recoverable failure |
| --- | --- | --- | --- |
| Quick Look | Set `List.Item.quickLook={{ path }}` and expose `Action.ToggleQuickLook`; test an explicit Space shortcut in the browser-shell prototype. | Show it only for a real path that still exists. Escape closes the preview. Raycast documents the action but does not guarantee unmodified Space while the List search field is focused. | Quick Look needs read access to the item but no app-to-app Automation permission. `Action.ToggleQuickLook` has no error callback, so an unsupported format or unavailable cloud placeholder cannot be diagnosed precisely. Keep the row selected and leave Open available. See [Raycast List](https://developers.raycast.com/api-reference/user-interface/list) and [Raycast Actions](https://developers.raycast.com/api-reference/user-interface/actions). |
| Copy path | Use `Action.CopyToClipboard` with the POSIX path. Use `Clipboard.copy(path)` only when a programmatic flow needs to stay open. | Available for every real item. There is no destructive side effect to cancel. | Clipboard write needs no extra permission. The built-in action closes Raycast and confirms success; a programmatic call returns a Promise that can be caught. See [Raycast Clipboard](https://developers.raycast.com/api-reference/clipboard). |
| Move to Trash | Use a custom destructive action that calls `confirmAlert()`, then `trash(path)`. `Action.Trash` is suitable only if the product deliberately wants no custom confirmation. | Preflight that the item still exists. Never enable it for synthetic rows, filesystem roots, or protected Places. Cancelling the alert returns `false` and changes nothing. | The operation can fail on missing items, read-only volumes, permissions, or a volume without normal Trash support. Do not remove the row optimistically. Remove it only after `trash()` resolves; otherwise keep selection and show the actual error. See [Raycast Alert](https://developers.raycast.com/api-reference/feedback/alert), [Raycast Actions](https://developers.raycast.com/api-reference/user-interface/actions), and [Raycast utilities](https://developers.raycast.com/api-reference/utilities). |
| Open with system default | Use `Action.Open` without `application`, or `open(path)`. | `getDefaultApplication(path)` can supply a label and preflight that macOS has a handler. There is nothing to cancel once Launch Services accepts the request. | No Automation permission. If the item disappeared or no handler exists, keep the Raycast view open and show a failure toast. See [Raycast utilities](https://developers.raycast.com/api-reference/utilities). |
| Choose application | Prefer `Action.OpenWith path={path}`. It provides Raycast's native submenu. A custom picker can use `getApplications(path)` followed by `open(path, application)`. | Escape cancels the submenu without opening anything. `getApplications(path)` is also the compatibility test. | No Automation permission. If an app was removed after enumeration, refresh the list and fall back to the system default only after telling the user. See [Raycast Actions](https://developers.raycast.com/api-reference/user-interface/actions). |
| Open directory in Ghostty | Resolve bundle ID `com.mitchellh.ghostty`, then use `Action.Open` or `open(directory, ghosttyApplication)`. Ghostty declares directory support, and its macOS folder-open behavior creates a new tab by default or a new window when the user selects that preference. | Hide the action when the bundle ID is absent or Ghostty is not returned as compatible for the directory. Launch cannot be cancelled after dispatch. | Launch Services needs no Automation permission. Respect Ghostty's `macos-dock-drop-behavior` instead of overriding the user's tab or window preference. AppleScript can force an exact window or tab, but it requires TCC Automation approval and Ghostty still describes the 1.3 scripting API as new, so it should not be the default integration. See [Ghostty's macOS folder-open setting](https://ghostty.org/docs/config/reference#macos-dock-drop-behavior) and [Ghostty AppleScript](https://ghostty.org/docs/features/applescript). |
| Open directory in Zed | For normal opening, resolve bundle ID `dev.zed.Zed` and use `open(directory, zedApplication)`. If the product later promises an exact new workspace, invoke Zed's CLI without a shell as `zed -n <directory>`. Resolve the installed CLI or derive the documented bundled CLI from the current app path. | Check the bundle ID first. For the CLI variant, also check that the executable exists. There is no useful cancellation after the short launch request starts. | Launch Services needs no Automation permission. The CLI reports success as exit code 0 and error as 1. On a CLI error, show stderr and offer the Launch Services action. Zed documents directory opening and `-n` in its [CLI reference](https://zed.dev/docs/reference/cli). |
| Open directory in T3 Code | Do not ship an action called "Open in T3 Code" yet. The only stable action is launching the app itself after resolving bundle ID `com.t3tools.t3code`. | App presence is detectable, but directory compatibility is not. The installed nightly has no directory document type and no `t3` CLI on `PATH`. | Current upstream registers `t3code://` as the desktop renderer and OAuth callback scheme, not as a project-opening deep link. The secondary-instance handler only reveals the existing window; it does not consume a project path. The server CLI has `t3 project add <path>`, but that mutates the project list and does not navigate the desktop client, so it is not a substitute. Wait for a documented deep link, desktop CLI, or IPC contract. Evidence: [desktop protocol implementation](https://github.com/pingdotgg/t3code/blob/main/apps/desktop/src/electron/ElectronProtocol.ts), [Clerk deep-link and secondary-instance handling](https://github.com/pingdotgg/t3code/blob/main/apps/desktop/src/app/DesktopClerk.ts), [desktop packaging config](https://github.com/pingdotgg/t3code/blob/main/scripts/build-desktop-artifact.ts#L2022-L2130), and [`t3 project` CLI](https://github.com/pingdotgg/t3code/blob/main/apps/server/src/cli/project.ts). |

Local verification on 2026-08-21 found Ghostty 1.3.1, Zed 1.16.1, and T3 Code Nightly 0.0.34. Ghostty and Zed both advertise directory document support. T3 Code advertises `t3code` and `t3code-dev` URL schemes but no directory document type.

### Failure policy

All actions should validate the path immediately before dispatch. A failure must leave the current tab, selection, and navigation history intact. Show the concrete error in a toast, then offer only a safe retry or fallback. Trash is the sole action here that needs an explicit confirmation and commit-after-success UI update. Never fall back to Finder automatically.
